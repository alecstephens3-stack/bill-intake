# Bill Intake

A small desktop pipeline for the vendor bills a practice's bookkeeper deals with every week:
**read each bill in the intake folder, file it under the house naming rules in the right vendor
folder, and enter the real bills in QuickBooks Online, only after a person has looked at the
proposal and pressed Go.**

The reading is the only messy part, so it is the only part a model does. Everything with a known
answer (where a file goes, what it is called, whether it is a bill at all, whether QuickBooks
already has it) is plain code with tests. Anything the code cannot answer with certainty becomes a
row that waits for a person, with the reason in plain words.

It is derived from a system in production at a healthcare practice, rebuilt generically with no
client content. Every vendor, folder and amount here belongs to "Example Clinic", a made-up
practice that the tests build on disk at run time. The repository holds no documents.

```
intake folder
  -> text        text.py      text layer out of each PDF or .txt (stdlib, pypdf if installed)
  -> reading     reader.py    Claude on AWS Bedrock fills a small JSON schema; validated, never trusted
  -> rows        rules.py     vendor folder, file name, year folder, bill or not: no model involved
                 plan.py      ready, or "needs a person" with the reason
  -> review      review.py    local web page: tick, rename, pick a folder, type an amount, Go
  -> files       files.py     no-clobber moves, a log of every move, Undo
  -> bills       quickbooks.py  idempotent creates through the QuickBooks Online API
```

## File map

```
bill_intake/text.py             PDF and text extraction; scans are flagged, not guessed
bill_intake/reader.py           schema, prompt, validation, BedrockReader, FakeReader, parallel reads
bill_intake/rules.py            the rules file, vendor matching, naming, what becomes a bill
bill_intake/plan.py             one proposal row per file; review edits; never-overwrite naming
bill_intake/review.py           the review page and its local server
bill_intake/files.py            moving files, the run log, Undo
bill_intake/quickbooks.py       OAuth 2.0 client, duplicate checks, bill creation, bill Undo, fake company
bill_intake/single_instance.py  one copy at a time
bill_intake/pipeline.py         the stages in order
bill_intake/samples.py          Example Clinic: rules, folders and sample bills, generated by code
tests/                          offline suite; a guard fails any test that opens a non-local socket
```

Dependencies: none for the core. `boto3` for the real Bedrock reader, `requests` for the real
QuickBooks client, `pypdf` optionally for harder PDFs, `pytest` for the tests.

## The decisions that matter

### 1. The model reads. It never decides.

`reader.py` asks for a dozen fields (vendor, document type, dates, amount, invoice number, three
yes/no flags, a short note) and nothing else. The reply is input, not truth: `validate()` checks every field against
the schema and throws out what does not fit. A date that is not `YYYY-MM-DD`, a document type
that is not invoice, statement or payment, an amount that is not a number: each is dropped and
recorded, and the row then waits for a person because the field is missing. Nothing downstream
ever sees a guessed value.

The yes/no flags are read in the direction of caution. "Already paid" lets a bill with no amount
due through, so only a real `true` counts. "Patient information on the page" and "this page is
not a bill" make a row more careful, so anything short of a clear no counts as yes.

Two prompt rules exist because the obvious behaviour is wrong for bookkeeping:

- **A due date is only ever the printed one.** Computing one from "Net 30" looks helpful and
  creates bills with dates nobody wrote.
- **Date confidence is its own field.** "Labelled", "single unlabelled", "ambiguous" and "none"
  are separate answers. Only the first two get filed; a page with three unlabelled dates is a
  question for a person, not a coin toss.

The model runs at temperature 0, one document per call, so every answer belongs to exactly one
file and one odd document cannot spoil the reading of the others.

### 2. The rules live in a file the bookkeeper owns

`rules.py` reads a plain text file (an example is in `samples.py`) with the paths, the year
folder pattern, a vendor-name exception table, and the vendor lists that decide what becomes a
bill. It is re-read on every run; nothing about a vendor is remembered anywhere else. When a
person picks a folder for a vendor the rules could not place, that choice is written back into
the same file, so the next run places it without help.

Vendor matching goes in a fixed order and stops at the first certain answer: the exception
table, then a normalised exact match (case, punctuation, `&`, and suffixes like Inc and LLC
ignored), then a spacing-insensitive match, then a single folder whose whole name appears inside
the vendor's name. Two candidate folders is not a match. It is a row for a person that names
both. Every list lookup is whole words only, because a short vendor name matching inside a
longer one is exactly the kind of error that enters a bill twice.

### 3. Not every filed document is a bill

Filing and entering are different questions. Most vendors send invoices that are entered one by
one; their monthly statement only says what to pay, and entering it as well would count every
invoice twice. A few vendors are the other way round: the statement total is what gets entered,
so their individual invoices are filed but never entered. Some vendors are never entered from
paper at all (autopay that arrives through the bank feed), and a payment record is never a bill.
`Rules.not_a_bill()` encodes those four cases, and each filed-only row says why on the review
page so the person can see the rule working.

Statements are filed under the end of the period they cover, not the day they were printed, so
February's statement lands in February even when it arrives in March.

### 4. Never overwrite, never two copies

The naming convention is `YYYY.MM.DD_Vendor Name.pdf`, with `_stmt` for a statement and `_pymt`
for a payment record. Two bills from one vendor on one day are normal, so `resolve_collisions()`
adds `_1`, `_2` against both the files already on disk and every other row in the same batch.

The move itself is more careful than it looks. `os.rename` replaces an existing destination
without a word on macOS and Linux, so it is not used. `move_file()` makes a hard link (which
fails atomically if the destination exists) and then removes the original; across drives it
copies into a file opened with exclusive create and deletes the half-made copy if anything
fails. A collision that appears between planning and moving is an error, never a replaced file.

Three more rules keep a run reversible:

- **The year folder must already exist.** A bill dated in a year with no folder waits for a
  person. Creating a year folder is a filing decision, not a side effect of a typo in a date.
- **The first failed move stops the run.** A folder that cannot be written to fails the same way
  for every file after it.
- **Every move is logged** as one JSON line with absolute paths. `undo_last_run()` reads the log
  back, moves each file home, reports any it cannot, and logs that too, so a second Undo picks up
  where the first stopped.

Files the person did not approve go to `intake/Not filed`, so the next run starts with only new
files instead of re-reading the same leftovers.

### 5. A person approves anything that moves a file or creates a bill

Nothing moves and nothing reaches QuickBooks until someone presses Go on the review page. The
page can untick a row, rename a file, pick a folder, or type an amount the reader could not find.
A row that still has no date or no folder cannot be ticked into "ready".

The page runs on `127.0.0.1` on a random port, and because it can now write to the accounting
system it is treated as an attack surface:

- every request must name this server as its `Host`, which blocks DNS rebinding;
- every POST must carry a token baked into the page when it was served, and an `Origin` (if the
  browser sends one) that is this server, so another open tab cannot press Go;
- the decision is accepted once;
- file names and vendor text reach the page as JSON data and are written with `textContent`, so a
  file named like a script stays a file name.

### 6. QuickBooks writes are idempotent and never silent

`quickbooks.py` talks to the documented QuickBooks Online Accounting API (v3) with OAuth 2.0.

- **The rotated refresh token is saved before it is used.** Intuit rotates the refresh token on
  every refresh, and the old one can stop working. The new one goes to the token store first, so
  a crash right after a refresh cannot strand the connection.
- **Every create sends a `requestid`** derived from the run, the payload and the attempt, so a
  resend after a dropped connection cannot make a second bill. A deliberate retry later is a new
  attempt with a new id, because the API can replay a stored refusal for a reused id.
- **Every bill carries a tag** in its private note (`run <id>, as <file name>`). If a create
  succeeded but its reply was lost, the next attempt finds the tag and adopts the bill instead of
  making another.
- **Duplicates are checked against the company, not just this run.** Same vendor, number, date
  and total is skipped as already there. Same number with a different total or date, or no number
  with the same vendor, day and total, is a "possible copy" for a person. Nothing in between is
  decided silently.
- **It never creates a vendor or an account.** A vendor QuickBooks does not know is a row for a
  person; a misspelled duplicate vendor is worse than one bill entered by hand.
- **A lost connection stops the batch;** one bad row does not. 429 and 5xx answers back off and
  retry; a 401 refreshes once and retries.
- **Undo deletes only unpaid bills.** A bill with a payment applied since is kept and reported.

Long invoice numbers keep their end (QuickBooks stores 21 characters, and long numbers carry
their unique digits at the end). Without a printed number, the file name stands in and keeps its
start, the date and vendor, plus any `_1`.

### 7. Patient information stays where it belongs

The real reader runs on AWS Bedrock inside an account covered by a business associate
agreement, with invocation logging off. The pages may hold patient names; the outputs do not. The
schema tells the model to flag such pages and write none of it, and the code does not rely on
that instruction: on a flagged page the model's free-text notes are dropped before they reach the
log, and QuickBooks only ever receives the vendor, dates, number, amount, account and the new
file name (which is built from the date and the vendor folder). It never sees the document. The `FakeReader` used by the tests and the demo never leaves the machine.

### 8. Cost and wall-clock time

Most of the time per bill is waiting on the reply, so `read_all()` reads several documents at
once with a small thread pool, then returns results in folder order. The pool is small on
purpose: it stays under the account's rate limits, and the SDK's standard retry mode waits out a
"slow down" instead of failing the run. Each call is cheap by construction: a short schema, a
capped number of pages and characters, a small output limit.

A key or model-access error is different from a bad document. It raises `ReaderUnavailable`,
which stops the run at once, and files not yet sent are never sent, since every one of them
would fail the same way. A PDF with no text layer (a scan) is flagged for a person without a
model call; the reader interface accepts page images, so a renderer can be plugged in where scans
are common.

### 9. One copy at a time

A second launch while the first copy is still reading (a double click that seemed to do nothing)
must not start a second run over the same folder. `InstanceLock` takes an OS file lock and
publishes the first copy's page address; the second copy opens that page and exits. An OS lock
is released when the process ends, even in a crash, so there is never a stale lock file to clear
by hand.

## What this rebuild leaves out

Windows packaging and updates, secrets in the OS keychain (the `TokenStore` interface is where
that plugs in), rendering scanned pages to images, and the settings screens of a desktop app.
The decisions above are the parts worth reading.

## Running it

```bash
python3 -m pip install pytest
python3 -m pytest
```

The suite builds Example Clinic in a temporary folder, generates its sample bills (small PDFs and
text files) with code, and runs every stage, including the review server on `127.0.0.1` and the
QuickBooks client against a scripted HTTP session. An autouse fixture fails any test that tries
to open a socket to anything other than the local machine.

To watch a whole run without any credentials:

```bash
python3 -m bill_intake demo
```

A real run reads with Bedrock, reviews in the browser, and enters bills in a QuickBooks sandbox
company:

```bash
pip install boto3 requests
export QBO_CLIENT_ID=... QBO_CLIENT_SECRET=...
python3 -m bill_intake connect --redirect-uri https://your-app.example.com/callback
export QBO_REALM_ID=...
python3 -m bill_intake run --rules filing-rules.txt --model <bedrock model or inference profile id> --quickbooks live
python3 -m bill_intake undo --rules filing-rules.txt --quickbooks live
```
